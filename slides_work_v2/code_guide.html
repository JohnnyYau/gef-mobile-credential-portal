層檔案它只做一件事
介面static/*.html、static/js/*.js五個一屏頁面（驗證／簽發／舞台／控制台／職員），沒有框架、沒有 build step。
HTTPapp/main.py（1,808 行）路由、驗證輸入、授權、限流、把自己組好的 JSON 交出去。業務判斷幾乎不在這裡。
服務issuance_service、query_service、signer_service、disclosure、capability、statuslist、anomaly、notifier、chat_service…每一支服務對應一個能力（簽發／查詢／簽名方／披露／持有者連結／狀態列表／異常／通知／問答）。
核心app/crypto_util.py、app/blockchain_util.py、app/chain_core.py雜湊、簽名、區塊、驗證。這裡沒有 HTTP、沒有 UI，可以單獨拿去跑測試。
儲存app/repository.py + data/區塊是 JSON 檔，索引／收據／審計是 JSON 檔（可切 sqlite），金鑰是 PEM。

一次請求的生命：GET /api/verify/{hash}

  1. main.py 的路由收下 hash，_validate_hash() 只收 16–200 個 [A-Za-z0-9_-]，形狀不對就 422，不進核心。
  2. query_service.verify_hash()：先問 blockchain_util.fetch_status() 「這串編號有沒有 ISSUE / REVOKE」。
  3. fetch_status() 走 _status_index()：一次掃完所有區塊，建出「雜湊 → 簽發高度／撤銷高度」的索引，結果按目錄指紋快取。
  4. 要判完整性時呼叫 verify_chain()：從第 0 塊重算，每塊驗連結、高度、簽名。有快取，但新塊一寫入就失效。
  5. 要驗某一塊的簽名時，_verify_payload_signatures() 用 crypto_util.fetch_pubkey() 取公鑰、verify_ds() 驗簽。
  6. 結果回到 query_service 組成 {verdict, status, checks, reason}，main.py 原樣輸出。
  7. 前端 simple_verify.js 只做兩件事：把 verdict 畫成一張卡、把四行過程填上。

整條路徑上沒有任何一層「相信」上一層：核心自己驗簽，服務層自己算，HTTP 層只轉發。

crypto_util.py — 只管「同樣的 JSON 算出同樣的位元」

函數做什麼 · 為什麼這樣做
:72 json_rfc8785() / :77 hash_json()先做 RFC 8785（JCS）正規化——鍵排序、數字格式固定——再算雜湊。沒有這一步，同一份憑證在兩台機器會算出兩個編號。
:102 merkle_root()三段欄位雜湊兩兩合成一個根，當 HashedDocument。好處：改姓名只動個人段，能指出「哪一段被改」。留單節點時直接回傳該節點。
:120 signature_message()真正被簽的不是 payload 雜湊，而是 HMAC(key=nonce, msg=payloadHash)。所以同一份文件每次簽名都不同，簽名本身不能用來關聯兩張憑證。
:307 sign_json() / :333 verify_ds()按金鑰型別分派：ML-DSA（FIPS 204）、RSA-PSS、ECDSA。演算法字串只用來對照登記表，實際驗簽看的是金鑰型別。
:144 gen_dskey() / :208 getfgpt()產生簽名金鑰；指紋是 SPKI 的 SHA-1／SHA-256，這就是簽名方在鏈上的身分。
:266 fetch_pubkey()讀 PEM 並解析。U31 之後按檔案 (mtime_ns, size) 記憶——否則每次驗鏈都重讀同一把公鑰，63 塊要 3.6 秒。

blockchain_util.py — 區塊與驗證

函數做什麼
:204 init_block()、:255 register_signer()寫 genesis、把簽名方登記進 info.yaml（含 retired_at_height）。
:337 issue_payload()、:360 revoke_payload()組 payload：action（ISSUE／REVOKE）、HashedDocument、三段雜湊、時間戳。撤銷不改舊塊，只寫新塊說它作廢。

:721 verify_document()對外的六項：鏈完整、簽名方受信、鏈上有紀錄、內容雜湊相符、簽名有效、未被撤銷。

Q&A

被問到代碼時的十一個答案每條 20–30 秒，不要展開

6 / 6
1. 為什麼要 JCS 正規化？
沒有它，鍵的順序不同就會算出不同雜湊，同一份憑證在兩台機器會得到兩個編號。RFC 8785 把這件事釘死。
2. 為什麼三段雜湊再合成一個根？
改姓名只會動個人段，改成績只會動學術段；出問題時能指出是哪一段，而不是只說「整份不對」。
3. 簽名為什麼要多包一層 HMAC(nonce)？
讓同一份文件每次簽名都不同。否則兩張憑證簽名一樣，外人就能把它們關聯起來。
4. 撤銷為什麼不刪塊？
刪掉就無法證明它曾經存在。撤銷是寫一塊新的說它作廢，歷史保留。
5. 怎麼防有人偷改舊塊？
改一塊，它的雜湊就變，下一塊的 prevHashSum 對不上；verify_chain() 從 0 掃到尾，會指出第一個壞塊。
6. 簽名方退役了，舊塊怎麼辦？
info.yaml 記 retired_at_height：退役前的塊仍算受信，之後簽的不算。這是「停止信任」與「鏈壞了」的分別。
7. 鏈上真的沒有個人資料？
只有三段雜湊、簽名與時間。姓名學號在機構側的 rawjsondocs/ 與學生手上的 PDF。
8. 驗一次要做多少事？
六項檢查：鏈完整、簽名方受信、鏈上有紀錄、內容雜湊相符、簽名有效、未被撤銷。任何一項不過就是 INVALID／REVOKED。
9. 為什麼驗證要幾百毫秒、不是 14 毫秒？
寫入後第一次查驗要從 genesis 重算全鏈；空閒時 40–120 ms，機器有負載時到幾百毫秒。海報上的 14 ms 是安靜機器、27 塊時量的。
10. RAG 是必需的吗／真的用了 LLM？
不是必需：沒有模型時退回模板式回答，仍然附鏈上出處。有 Ollama 或 DeepSeek 時才是生成式。
11. 哪一部分是 demo 級？
限流是記憶體、會話是記憶體、通知預設 dry-run、sqlite 是可選、備份是 tar。這些我們會直說，不假裝是生產級。

最後一句，講完就停

「這套東西沒有一行在假裝自己是 blockchain：它是一條只增不改的雜湊鏈，加上後量子簽名，重點是驗證的人不需要懂密碼學——掃一個碼，六項檢查，一句結論。」

不要做：不要現場改代碼、不要打開 data/ 給人看裡面的姓名、不要把 ADMIN_TOKEN 打在畫面上、不要說「我們用了 AI」卻舉不出哪一行。
