Mobile Credential Verification Portal
How the whole thing works

A diploma is a claim. Today, checking that claim means an email to a registry office, a PDF that anyone can retype, or a phone call that nobody makes. This system replaces that with a square on a page: you scan it, and within a second the browser answers “this credential is valid” or “this credential has been revoked” — without installing anything, without logging in, and without having to trust the server that answered.

1The problem, stated precisely

Universities issue credentials; employers, other universities and border officers check them. The check is slow, manual and unevenly applied. Meanwhile the artefact being checked — a PDF, a scanned letter — is trivially editable, and the edit is invisible: retyping 1ST HON to 1ST HON. changes nothing about how the document looks.

So the requirement is not “store credentials online”. It is narrower and harder:

The requirement

Given one artefact in front of me, decide whether this exact content was issued by that institution, and is still valid right now — using only public information, in under a second, on a phone, with no account.

Everything in the system follows from those four constraints. “Using only public information” is why the design is cryptographic rather than a database lookup. “Under a second on a phone” is why there is a QR code instead of a file upload. “Still valid right now” is why revocation is a first-class operation rather than a delete.

2Threat model: what is actually being defended

A design is only meaningful against named attacks. These are the ones this system answers, and the ones it does not.

Attacker does thisSystem's answerResidual risk
Edits one character in a credential PDF or JSON The document's hash changes, so check 4 (hash_match) fails and check 5 fails too None that matters — this is the core guarantee
Re-signs a forged credential without the institution's key Signature verification needs the private key; only the public key is published None, assuming the key is not stolen
Copies a valid QR code from someone else's certificate Nothing — a QR proves the credential, not who is holding the phone Real and unavoidable. The page says “this credential is valid”, never “this person is who they claim”
Steals the issuer's private key retire_signer(at_height) marks the key untrusted from a given height; blocks signed before it stay valid Anything signed between theft and detection looks valid. Detection latency is the exposure
Deletes or rewrites a block file Chain replay links heights, so a missing or edited block fails verify_chain; the API returns 503, not “not found” An attacker who rewrites every block consistently and re-signs the whole chain would need the key anyway
Runs a dishonest server that returns “VALID” for everything Partially. The JSON is only a claim; the evidence (blocks, public keys) is portable and verifiable with the same open code If you only read our website and never verify, you are trusting us. That is why the status list and receipts are signed and the source is public
Replays an old “valid” answer after a revocation Revocation is an appended block; any fresh read sees it A client caching a status list offline can be stale until it refreshes — the same window any OCSP-style list has

The honest summary: the cryptography removes the need to trust the server for correctness of content; it cannot remove the need to trust the institution that holds the key, nor can it turn a credential into an identity document.

3The credential: three sections and a canonical form

A credential is one JSON object with exactly three sections. The split is not cosmetic: it lets verification say which part disagrees when something is wrong.

{
  "PersonalParticulars": { "Surname": "CHAN", "GivenNames": "TAI MAN", "Sex": "M",
                           "DOB": "19880808", "StudentID": "22000000" },
  "AcademicInfo":        { "DegreeName": "Bachelor of Engineering / Electronic and Electrical Engineering",
                           "DegreeStartDate": "20220815", "DegreeEndDate": "20260801",
                           "Honour": "1ST HON", "Observations": "NO OFFICIAL OBSERVATIONS" },
  "DocumentInfo":        { "DateOfIssue": "20260901", "AuthorizedSignature": "…",
                           "IssuingO": "UNIVERSITY OF UTOPIA", "IssuingOU": "DEPT OF EE",
                           "DocType": "CERTIFICATE OF DIPLOMA" }
}

Before anything is hashed, the object is serialised with RFC 8785 JSON Canonicalisation (JCS): keys sorted, numbers in one canonical form, strings escaped one way. Without this step a hash would depend on key order and whitespace, and the same credential typed on two machines would produce two different identities. Canonicalisation is what makes “the same content” a well-defined idea.

JSON objectthree sections, any key order
→
JCS bytesone canonical byte string
→
SHA3-512one digest
→
base64urlno padding, URL-safe

Padding is stripped so the digest can live in a URL, a filename or a QR code without escaping. That choice is visible everywhere downstream: every identifier in this system is a 86-character base64url string.

4Identity: from document to one string

Each section is hashed separately, then the three digests are combined by a Merkle step into one root. That root is the credential's identity: HashedDocument.

h_pp  = hash_json(PersonalParticulars)      # sha3-512
h_ai  = hash_json(AcademicInfo)
h_di  = hash_json(DocumentInfo)
root  = merkle_root([h_pp, h_ai, h_di])     # odd level duplicates the last leaf

Two properties make this worth the extra step. First, the root is reproducible by anyone: run the same three lines on the same document and you get the same 86 characters. Second, the parts stay separable — if the root does not match, the system can say that AcademicInfo is the section that disagrees, rather than “the document is wrong”.

Measured, not asserted

In this deployment the diploma's root is GFiY4d67yoi8X4wmwnL_8IX18_xo_F7HOQgWBdHZXubNTLhvVX_K1PCWuKZa8cntDWyq5Mnr7i8yvAopAjxrGQ. Changing the surname from CHAN to CHAN. keeps two section hashes identical and changes the third and the root. That experiment is shipped as scripts/learn/01_document_to_number.py and takes eight seconds to run.

5Signing: two layers, and why

The naive design signs the payload hash directly. This system signs HMAC(key = nonce, message = payload_hash) instead — a second layer, with a fresh random nonce per signature.

nonce     = 32 random bytes, base64url          # per signature, never reused
message   = base64url( HMAC-SHA3-512(key=nonce, msg=payload_hash) )
signature = Sign(private_key, message)          # ML-DSA-65, or RSA-PSS

The reason is binding, not secrecy. A bare signature over payload_hash can be lifted and replayed in any context that happens to verify the same hash. A signature over HMAC(nonce, hash) is welded to one nonce, and the nonce is recorded in the block. Move the signature to a different nonce and it fails — verified in scripts/learn/02_sign_the_number.py, where the same document signed twice produces two different signatures, both valid, and neither usable with the other's nonce.

Field in the blockMeaning
DSAlgoAlgorithm label, e.g. ML_DSA_65
DSsha256fgptSHA-256 fingerprint of the signer's public key (SPKI)
DSnonceThe per-signature nonce; required to recompute the message
DSignaturebase64url signature bytes (ML-DSA-65 signatures are ~4.4 kB)
DSmessageDigestThe signed message itself, so a verifier can compare without re-deriving
DSschemehmac-nonce-wrap-v1 — a version switch; older blocks without it read as v1

Algorithms. The primary signer is ML-DSA-65 (FIPS 204), chosen because credential lifetimes are long and RSA/ECDSA are the algorithms a future quantum machine attacks first. A second signer, RSA-PSS-2048, runs alongside it: the block format is algorithm-labelled per signer, so rotation is a registry operation, not a migration. Verification dispatches on key type, and any exception — malformed, wrong length, unknown algorithm — returns False. There is no “probably fine” path in a signature check.

Key lifecycle

Retiring a signer must not retroactively invalidate history. The registry entry keeps the public key and gains a retired_at_height boundary; blocks at or below that height still verify, blocks above it are refused. Re-registering the same key clears the boundary. This is the difference between “we stopped trusting this key” and “the chain is broken” — the first is routine hygiene, the second invalidates every verdict in the ledger.

6The ledger: blocks and links

The ledger is a directory of JSON files, one per block, named by zero-padded height. There is no database, no daemon, no network protocol. A block looks like this:

{
  "height": 1,
  "contentHashAlgo": "sha3_512",
  "prevHashSum": "BpHCjQB2AfwYaa…",      # sha3-512 of the ENTIRE previous block JSON
  "timestamp": 1795…,                     # time.time_ns()
  "schemaVersion": 2,
  "payload": { "action": "ISSUE", "HashedDocument": "GFiY4d67…", … },
  "DataSignatureInfo": [ { "DSAlgo": "ML_DSA_65", … } ]
}

Appending is a fixed sequence, and the order is deliberate:

  1. Read info.yaml for the current height and hash algorithm — never trust the caller's values.
  2. Load the previous block and hash its whole JSON, not just its signature.
  3. Sign the payload once per signer, each with its own nonce.
  4. Write the block file atomically: write .temp, then os.replace.
  5. Only then update last_block_height in info.yaml, also atomically.

Step 5 last, because the two failure modes are not equally bad. “Block written, height not updated” is recoverable — the file is there and the height is one behind. “Height points at a block that does not exist” makes every read raise, and the chain looks corrupt when it is merely inconsistent. The same reasoning explains why the hash covers the whole previous block: hashing only the signature would leave the timestamp uncommitted, and a block's timestamp is part of what was issued.

Demonstrated live

Tamper with one character in block 1 and block 2 turns red without being touched — block 1 fails next_link and signatures, block 2 fails prev_link. scripts/learn/03_link_the_blocks.py does this on a copy in %TEMP%, then runs the full six checks against the tampered copy.

7Verification: six checks

Every verification returns the same six booleans plus a verdict. They are independent pieces of evidence, not one judgement repeated.

CheckWhat it provesWhat it does not prove
chain_integrityEvery block from genesis links and verifiesThat this credential exists — it is a precondition
signer_trustedThe issuing block's keys are in the registry (and were trusted at that height)That the institution is honest
on_chain_recordAn ISSUE block exists for this hashThat the presented document matches it
hash_matchThe document you hold reproduces the hashes recorded on chainAnything, if no document was supplied (reported as null)
signature_validThe block's signature verifies under the published public keyThat the key holder had authority — that is a policy question
not_revokedNo REVOKE block references this hashThat the credential was ever legitimate — that is check 3 plus 5

Two entry points, deliberately different

GET /api/verify/{hash} answers everything computable without the document. Because no document is supplied, check 4 has no input:

"hash_match": None,   # requires the full document — not True, not False

Reporting null rather than True is a deliberate discipline: a result sheet with six ticks should mean six things were computed. The front end honours it with a third branch — true says “signature verified”, false says “verification failed”, anything else says “no signature to verify”. Collapsing that third case into “yes” is the kind of silent claim that makes a verification system worthless.

POST /api/verify/document takes the whole credential, recomputes the three section hashes, and then check 4 becomes a real boolean. That is the endpoint an employer uses when they hold the PDF, and the one the phone page uses when the page was opened with a hash and a document together.

The route itself

996  @app.get("/api/verify/{hashed_document}")
997  def verify_hash(hashed_document: str):
998      _validate_hash(hashed_document)                  # shape: 16–200 chars of [A-Za-z0-9_-]
999      result = chain_service.verify_hash(hashed_document)
1000     if result.get("verdict") == "REVOKED":
1001         result.update(chain_service.revoke_meta(hashed_document))
1002     result["receipt_id"] = receipt_registry.register(...)   # a signed receipt of this answer
1004     verification_log.record(...)                     # anonymised
1006     return result

Eleven lines, zero arithmetic. The route validates shape, delegates, stamps a receipt, logs, and returns. If you deleted the web layer the ledger would still be correct — which is the whole point of keeping the arithmetic in three modules with no HTTP or UI imports.

8Revocation: append, never delete

Revoking appends a new block whose payload is {"action": "REVOKE", "HashedDocument": …}. The ISSUE block is untouched. Two consequences: the credential's history stays provable (you can show that it was issued, and when it stopped being valid), and revocation cannot be “undone” by editing a file — only by another append.

A single pass builds the status index — hash → issue heights, revoke heights, first issue timestamp — so “issued?” and “revoked?” are answered by one scan rather than two, cached against the block directory's fingerprint. An unreadable block is not skipped during that scan: a corrupt chain must return 503, never “not revoked”. Swallowing that exception would turn a data failure into a positive verdict.

Offline status for employers

GET /api/statuslist returns every revoked hash with reason and effective time, plus the chain height and last block hash, signed as one envelope (gef26.statuslist.v2). An employer can cache it and answer “revoked?” without calling us. The v1 signature of this list carried no nonce and no fingerprint, which made it unverifiable by anyone — a signature that cannot be checked is decoration, and it silently falsified the offline promise. v2 signs with the nonce, the real key fingerprint and the registry name travelling alongside, and publishes the keys at GET /api/signers/keys.

9Storage: five stores, two backends

The ledger is files on disk; everything around it (API keys, receipts, the anonymised log, notification outbox, revocation index) goes through one abstraction with two interchangeable implementations.

StoreRecordsBackends
ApiKeyStoreemployer key id → digest, name, timestamps, revokedJSON file / SQLite
ReceiptStorereceipt id → hash, verdict, endpoint, timeJSON file / SQLite
LogStoreanonymised verification log (append-only JSONL)JSONL / SQLite
NotificationStorenotifier outbox and audit trailJSONL / SQLite
RevocationIndexStorehash → issued height, revoked flagJSON file / SQLite

The JSON implementations read and write the existing files in their existing formats, so switching backends changes nothing observable to callers. The SQLite implementations use only the standard library, one short-lived connection per operation, and a per-store lock — so a crash cannot leave a half-written row, and threads never share a connection. This layer is deliberately not yet wired into every endpoint: reads first, then writes, because a migration you cannot roll back is not a migration.

Corruption is handled as a distinct outcome. Missing or unparsable block files raise ChainDataError, which the API maps to 503. A verifier must never be told “this credential is not on the chain” when the truth is “I could not read the chain”.

10The HTTP surface

Fifty-six route decorators. They group into five families, and the grouping is the auth model:

FamilyExamplesAuth

Employer (API key)/api/verify/batch, /api/receipt/{id}, API key adminkey digest + per-key rate limit
Explanatory/api/chat, /api/rag/status, /api/metrics, /api/diagnosticsmixed; chat is grounded, never a verification path

Hardening is middleware, not per-route politeness: body-size and JSON-depth limits, origin checks, per-client rate limits, and a public mode (PUBLIC_MODE=1) in which every admin endpoint returns 403 and the UI hides the admin surfaces entirely. In public mode the attack surface is the verification surface.

11The front end

Five pages, plain HTML/CSS/JS, no framework and no build step: verify, issue, the stage control panel, the staff console and the holder page. The verification page is the one that matters at a booth: it is a single screen, it renders one card, and it never asks the visitor to press a button.

It contains no cryptography. A verdict arrives as a string — "VALID ON CHAIN", "REVOKED", "INVALID", "NOT FOUND" — and a lookup table turns it into a headline. That separation is testable: change the table and the page lies, while the chain stays correct. It is one of the reasons the checks live in a module that imports neither HTTP nor DOM.

Mobile behaviour was measured rather than assumed: at a 390×844 viewport the page's scrollWidth equals the viewport width, and the four check rows collapse to a single column. A QR code opened from a poster has to fit a phone that a visitor is holding at an angle.

12Performance, and why the caching is shaped this way

First measurements were unacceptable for a booth: the receipt took 3.5 s, then 11.1 s, on a chain of 63 blocks. The cause was structural, not a leak. Every append changed the block directory, which invalidated the chain-integrity cache, and a cold scan re-read and re-parsed every signer's PEM for every signature.

Two fixes, both keyed on evidence rather than time alone:

  • Directory fingerprint. The cache key is (block count, total bytes, newest mtime_ns). Any append, rewrite or truncation changes it, so a verdict-carrying cache cannot go stale by construction. A short TTL sits on top only to bound the one case the fingerprint cannot see — an edit that preserves every file's size and mtime.
  • Public-key memoisation. Keys are cached by (mtime_ns, size) of the PEM file, so a replaced key is picked up immediately. Caching by path alone would mean silently trusting a key that had been swapped underneath us.

The remaining cost is honest work: ML-DSA verification is not free, and a chain that grows will need either incremental verification or a checkpoint signed by the registrar. Both are on the list; neither is disguised as done.

13Privacy

Only hashes and public metadata go on the chain. PersonalParticulars and AcademicInfo stay in the institution's own store; the block carries their digests plus DocumentInfo, which is the issue date, the issuing office and the document type. Surname, given names, date of birth and student ID are never written to a block.

Two mechanisms exist for the “I need to show this, but not all of it” case. Selective disclosure commits each field with a salt (gef-field-v1) so a holder can reveal one field and prove it belongs to the committed record without revealing the rest. Capability links are HMAC-SHA256 tokens over {sid, h, exp, v}: they grant a holder access to their own page for a fixed window, and every failure returns the same 404 so a token cannot be probed for validity.

What remains linkable: a credential hash is stable, so two verifications of the same credential are recognisably the same credential. The public log therefore stores hash prefixes, not full hashes, and the verification log is anonymised. This is a real tension — auditability versus unlinkability — and it is resolved toward “enough to detect abuse, not enough to build a profile”.

14What this is not

Say this plainly

There is no consensus, no peers, no gossip, no network synchronisation. It is an append-only hash chain with signatures, operated by one node. Calling it a blockchain would be wrong, and the wrong word invites the wrong questions.

The usual follow-up is “why not Ethereum?”. Three reasons, in order of weight:

  1. There is nothing to agree on. One institution issues its own credentials. Consensus solves disagreement between mutually distrusting writers; there is one writer.
  2. Personal data does not belong on a public chain. An append-only public ledger is permanent and world-readable; a hash of a student's record is a linkable identifier forever. Even hashes leak: a small candidate set can be brute-forced.
  3. Cost and latency. Gas, blocks and finality for a fact that one signature already settles.

Honest limitations, stated as limitations: a single node is a single point of failure; there is no incremental verification yet, so boot time grows with chain length; the issuer's key custody is a policy problem this code cannot solve; and physical possession of a QR still proves nothing about who is holding the phone.

15Engineering practice

The parts that are easy to skip are the parts that decide whether the demo survives a hostile question.

  • Tests: 39 test modules across the suite, run as one command, covering the crypto primitives, the chain lifecycle, revocation, capability tokens, the status list signature, batch verify, PDF extraction and the API surface.
  • Preflight: an eleven-item check that runs before a demo — chain integrity, signer registry, public URL reachability, QR decodability under a phone-camera simulation (downscale, blur, JPEG compression), and the revocation path rebuilt from the live chain rather than a hard-coded hash.
  • Failure as a first-class outcome: ChainDataError → 503; unknown algorithm → False, never “trusted”; missing document → null, never “passed”.
  • Number discipline: ~6,200 lines of code in app/ (9,885 including blank lines and docstrings), ~5,100 in tests, ~2,100 in scripts, ~3,900 in the front end. Quoting the larger number as “code written” would be padding.

18The whole thing in one paragraph

A credential is three sections of JSON; each is canonicalised and hashed, and the three hashes combine into one root that serves as the document's identity. That root is signed with a fresh nonce, so the signature is welded to one issuance and cannot be replayed. The signed payload is appended to a block that stores the hash of the entire previous block, which is what makes the history tamper-evident rather than merely stored. Anyone holding the public key can verify without trusting us; the six checks separate "we cannot find it" from "we found it and it is wrong"; and revocation is a new block, never a deletion. Everything above that — the HTTP routes, the five pages, the receipt, the QR code — only carries the answer around.

Ninety seconds, no jargon, and it is the same paragraph whether the listener is a professor, a parent or a recruiter.
