## 2. 为什么旧链一个字节都不能动

U4.1 的报告里已经确认：块哈希是对**整块 dict** 算的。这里同一个约束继续生效，并多出一层：

- `info.yaml` 也是链状态的一部分。给旧链补 `chain_id`/`params_version`，会让"链参数"与"链上已有的块"出现同一份元数据的两个版本——今天补、明天有人再补一次，`prevHashSum` 不受影响但 `chain_id` 可能被不同实现算成两个值，快照就无法对账。
- 所以策略是：**旧链只读派生，绝不回写**。`chain_params()` 在缺字段时按 `chain_name + algo` 派生 `chain_id`，版本号缺省为 1。派生是确定性的，同一份旧 `info.yaml` 永远得到同一个 `chain_id`。

冒烟里专门验了这一点：读参数前后 `info.yaml` 文本**逐字节相同**。

### 3.1 快照清单的字段选择

```
chain_id / chain_name / height / last_block_hash
content_hash_algo / params_version / schema_version
signers[] = {name, sha256fgpt, ds_algo}
```

每一项都对应一个外部方可独立核对的判断：

- `last_block_hash` —— 别人若持有同一高度的块，重算哈希即可比对，不需要整链；
- `signers[]` —— 声明"此刻谁有权签"，与注册表快照一致；
- `params_version` / `schema_version` —— 说明这份清单是按哪套参数和哪版结构读出来的，避免拿 v1 快照去对 v2 链。

### 3.2 一个被我抓到的真缺陷：nonce 丢失使快照不可验

第一版我图省事，用现成的 `signer_service.sign_payload()`：

```python
algo, signature = sign_payload(manifest)   # 只返回 (algo, sig)
```

问题在 `sign_payload` 的签名消息是 `HMAC(key=nonce, msg=payloadHash)`，nonce 由 `sign_json` 随机生成后**被丢弃**（原设计是"nonce 嵌在 payload 里"，那是 chainblock 的用法，不是通用签名）。

后果：**外部方拿着公钥和清单也验不了这个签名**——它缺少 nonce，算不出被签消息。这等于签发了一个无法验证的签名，比不签更糟。

修正：`snapshot_manifest` 改为直接调 `crypto_util.sign_json`，把 `(nonce, signature)` 都收下来，`DSnonce` 写进签名块。测试里用 `crypto_util.verify_ds(manifest, algo, pub, sig, nonce, algo)` 真的验了一遍，不是只断言"签名字段非空"。

## 6. 这步没有证明什么（必须写清）

1. **`chain_id` 不参与任何验证判定**。它现在只是被记录、被快照携带。要让"链身份"具备约束力，得在块里绑定并参与校验——那是又一次结构变更（而且必须只对新块生效），本步没做。
2. **`params_version` 没有升级闸门**。当前没有任何代码因版本不同而改变读取或验签行为；它只是元数据。真正需要版本分支（例如换哈希算法）时才该引入，现在引入等于空转。
3. **快照不落盘、不可轮换**。每次请求现算现签。若要对账"昨天的链"与"今天的链"，需要把快照存储并留时间序列——属于运维侧设计，不在本批。
4. **快照端点没有埋审计**。`/api/admin/chain-snapshot` 目前不写 `audit_events`。要补就得改 `audit.record` 的调用点，与 U3 那 8 项遗留（审计不含操作者身份）一起统一处理更合理。
5. **损坏注入只覆盖单块级破坏**，没覆盖"整块被替换成另一条合法链的块"（跨链拼接）。这类攻击需要 `chain_id` 参与校验才能识别，回到第 1 条。
