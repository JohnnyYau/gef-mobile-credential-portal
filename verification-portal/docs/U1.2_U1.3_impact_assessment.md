# U1.2 / U1.3 影响面评估 — 服务层拆分与端点请求模型化

评估日期：2026-11-13
基线：U1.4 末状态（108 用例 / 12 模块全绿；ruff app 4 得既有 unsafe；mypy 16 错误 / 7 文件）

## 1. 现状盘点

### 1.1 `chain_service.py` 体量与职责

单文件承担 4 类职责、24 个函数，约 545 行：

| 职责 | 函数 |
|---|---|
| 链初始化 / 样例种子 / 快照恢复 | `_ensure_signer`、`_seed_samples`、`ensure_revoked_sample`、`restore_snapshot_if_needed`、`ensure_chain`、`chain_info` |

### 1.2 外部对 `chain_service` 的依赖点（拆分必须全部保留）

- `main.py`：`ensure_chain`、`restore_snapshot_if_needed`、`chain_info`、`issue`、`hash_of`、`revoke`、`verify_hash`、`revoke_meta`、`status`、`verify_document`、`demo_credentials`、`ensure_revoked_sample`、`SAMPLE_REVOKED_DOC`、`chain_tail`、`student_credentials`、`list_signers`、`add_signer`、`set_active_signer`

- `chat_service.py`：`ensure_chain`
- `person_context.py`：`verify_hash`
- `statuslist.py`：`chain_snapshot_id`、`revoked_records`、`sign_payload`

- 测试：`ensure_chain`、`chain_info`、`CHAIN_DIR`、`demo_credentials`、`ensure_revoked_sample`、`SAMPLE_DIPLOMA`、`verify_document`

### 1.3 端点手动 JSON 解析点（4 处）

| 端点 | 当前写法 | 请求体契约 |
|---|---|---|
| `POST /api/custom/build` | `await request.json()` + `isinstance(dict)` | 自由字段字典 + `issue` 布尔 |
| `POST /api/verify/document` | JSON 分支 `await request.json()` 取 `document`；multipart 分支保留 | `{"document": {...}}` 或 multipart |
| `POST /api/verify/batch` | `await request.json()` 取 `hashes` | `{"hashes": [str...]}`，**逐行**容错 |
| `POST /api/admin/apikeys` | `await request.json()` 取 `name` | `{"name": str}` |

## 2. 拆分方案（U1.2）

### 2.1 目标结构

```
app/
├── chain_core.py        内部：锁、路径、签名者加载、链初始化与样例种子、快照恢复、chain_info
├── signer_service.py    内部：多签名者注册 / 激活 / 签名
├── issuance_service.py  内部：签发 / 撤销 / 撤销记录
├── query_service.py     内部：状态 / 文档核验 / 哈希核验 / 链尾 / 学生索引 / 快照 ID
└── chain_service.py     薄门面：全部旧名字 re-export，调用方零改动
```

### 2.2 依赖方向（单向，无环）

```
main / 其他调用方
        ↓
   chain_service（门面）
        ↓
signer_service / issuance_service / query_service
        ↓
    chain_core
        ↓
blockchain_util / crypto_util / config
```

`chain_core` 不 import 任何 `*_service`；因此不存在循环。`_lock` 只在 `chain_core` 创建一次，其他模块 `from .chain_core import _lock` 拿到的**是同一个 RLock 实例**，锁语义不变（这一点是正确性关键：若各自新建锁，签发与种子会并发写链）。

### 2.3 风险与缓解

| 风险 | 缓解 |
|---|---|
| 循环导入 | 依赖单向；`chain_core` 不引用 service 层 |
| 锁被重复实例化 | `_lock` 唯一创建点在 `chain_core`，其余模块引用同一对象 |
| 私有工具函数跨模块访问 | `_load_signer` / `_store_raw_document` / `_active_signer_fgpt` / `_signer_priv_path` 统一放 `chain_core`，供其他模块内部引用 |
| 旧名字丢失导致调用方崩 | 门面显式 `__all__` 全量 re-export；每步后跑单模块 + 全量回归 |
| 行为漂移 | 函数体逐行原样迁移，不改任何实现逻辑 |

## 3. 请求模型化方案（U1.3）

新增 4 个 Pydantic 模型，**但响应与错误契约逐字保持**：

| 模型 | 字段 | 保持行为的关键点 |
|---|---|---|
| `CustomBuildBody` | 文档化字段全部 `Any` + `extra="allow"` | 旧实现把原始 JSON 字典透传给 `custom_service`，字段值不做类型约束（`_clean` 自行处理）。用 `Any` 而非 `str` 可避免"客户端传数字/布尔时新增 422"。`issue` 同样用 `Any` 以保留原始真值语义。 |
| `VerifyDocumentBody` | `document: dict` | 旧的 `isinstance(document, dict)` 校验等价；非字典仍 422，`detail` 文案不变。 |
| `VerifyBatchBody` | `hashes: list[Any]` | 旧的**逐行**校验（非字符串行记 `ERROR` 而不是整单失败）依赖元素原样保留，故元素类型为 `Any`。 |
| `ApiKeyCreateBody` | `name: Any = None` | 旧实现 `payload.get("name") or "unnamed"` 直接透传任意值，`Any` 保持等价。 |

**关键约束**：不把模型放进入参签名（如 `body: CustomBuildBody`），因为那会让 FastAPI 用自家 422 结构（`detail` 变成列表）替换现有 `{"detail": "<字符串>"}`。改为在函数体内 `model_validate`，捕获 `ValidationError` 后转成**与旧文案一致**的 `HTTPException(422, detail="...")`。

multipart 分支（`/api/verify/document` 的文件上传）完全保持原样，只替换 JSON 解析层。

## 4. 验收判据

- 12 模块 108 用例全绿，且路由与响应字段与升级前逐一对齐。
- 端点错误文案逐字不变（对 4 个端点手工比对旧字符串）。
- `ruff check app` 不高于 4 个既有项；`mypy app` 不高于 16 错误。
- `chain_service.py` 行数显著下降（目标 < 150 行），职责单一。

## 5. 回滚

拆分前后若出现回归：`git checkout -- verification-portal/app` 并删除 `chain_core.py`、`signer_service.py`、`issuance_service.py`、`query_service.py`（均为新增未跟踪文件），即回到 U1.4 状态。
