## 2. 结构化校验

```python
validate_answer(answer, citations, record_count) -> {
  ok, citations, problems, citation_count, record_count, zero_citations
}
```

三条规则与两条**故意不做的**：

| 规则 | 判定 |
|---|---|
| 答案非空 | 空白字符串即 `answer is empty`，`ok=False` |
| 引用号落在返回记录区间 `1..N` | 越界即 `citation [7] is outside the 3 returned record(s)`，`ok=False` |
| 引用号为整数 | `[abc]` 记为 `not an integer`，`ok=False` |
| **零引用** | `ok=True`，但 `zero_citations=True` 且 problems 记 `answer cites no record` |
| **不补造引用** | 零引用时**不**自动把"全部记录"塞进 citations —— 那等于系统自己造来源 |

零引用被当作"可交付但要标注"的状态，因为对「链上无此学号」这类问题，正确回答本来就没有可引用的记录。

### 2.1 这里发现并修掉一个真缺陷：校验曾是空转

原实现：

```python
if backend in ("deepseek", "ollama"):
    citations = list(range(1, len(records) + 1))   # 无条件全给
```

于是 LLM 写出的 `[9]`（3 条记录时越界）根本进不了校验——**citations 是我们自己填的，校验永远通过**。这种"自己给自己签发合格证"的检查比没有检查更危险，因为它会让人相信有检查。

改为从答案文本里抽真实引用：

```python
parsed = extract_citations(answer)      # 正则 [n]，保序去重
citations = parsed or list(range(1, len(records) + 1))  # 模型没写才退回全给
```

现在 `[9]` 会真的越界 → `ok=False` → 该答案被丢弃、改走离线引擎（有测试覆盖）。

## 3. 离线规则链改数据表

旧结构是 12 段 if/elif，优先级靠书写顺序隐含。新结构：

```python
OFFLINE_RULES = [
 {"name": "exact-hash",   "match": ..., "answer": _r_hash},
 {"name": "courses",      ...},
 {"name": "person-or-sid",...},
 {"name": "unknown-sid",  ...},
 {"name": "revocations",  ...},
 {"name": "counting",     ...},
 {"name": "signer",       ...},
 {"name": "algorithm",    ...},
 {"name": "integrity",    ...},
 {"name": "latest-block", ...},
 {"name": "summary",      ...},
]
```

`_offline()` 只剩三行循环。两条契约：

- **顺序即优先级**，写在表里而不是散落在控制流里。`exact-hash` 永远第一——查询里出现 88 字符的哈希，是比任何关键词都强的信号。
- 处理器返回 `None` 表示"这一条其实不归我"，扫描继续。这让「问句含 course 但语料里没有任何课程字段」能自然落到后续规则，而不是被误答。

新增问题类别 = 追加一条表项 + 一个处理器；不需要碰 `_offline()`，也不需要担心在哪里插入。

## 4. 降级链

旧行为：DeepSeek 失败 → **直接**离线；Ollama 只有在没配 DeepSeek 时才被考虑。等于配了 key 的用户永远用不上本地模型兜底。

新顺序：**DeepSeek → Ollama → 离线**，每一跳失败都记一笔：

```json
"degraded": ["deepseek unavailable: ConnectError", "ollama unavailable: ConnectTimeout"]
```

配合 `backend` 字段，调用方可以区分三件不同的事：

| 情况 | `backend` | `degraded` |
|---|---|---|
| 没配任何后端 | `offline` | `[]` |
| 配了但连不上 | `offline` | `["deepseek unavailable: ..."]` |
| 配了、连上了、但答案空 | `offline` | `[..., "LLM answer failed structural validation; used offline"]` |

`/api/chat` 把这些透出为 `generation.degraded`，UI 可以据此提示"当前为离线兜底"，而不是假装一切正常。

## 5. 零引用兜底的定位

`chat_service` 原本就有「无引用就展示全部记录」的兜底。它不能删（UI 空来源比有来源更糟），但**不能无声**：新增 `generation.sources_are_fallback`，为 `true` 时那批 `sources` 是检索上下文而非答案实际引用。字段是新增，老前端读不到也不报错。

## 7. 明确没做到的部分

1. **没有真 LLM 联调**。本环境无 `DEEPSEEK_API_KEY`、无 Ollama 服务，降级链全靠 `mock.patch` 驱动。真实网络下 `httpx` 的异常类型（`ConnectError`/`ReadTimeout`）确实落在捕获的 `OSError` 子类里，但**未实测**。
2. **`degraded` 只记异常类型名，不记详情**。为了不把 base URL / 响应体泄进前端，刻意只写 `type(exc).__name__`；排查需要看服务端日志。
3. **规则表仍是关键词匹配**。同义问法（"certificate" vs "diploma"、"revoked" vs "cancelled"）不在同义词表里，"count " 这种带尾空格的关键词也只能命中特定写法。这是规则引擎的本分，不是失误，但意味着**自然语言覆盖度有限**。
4. **`validate_answer` 不检查答案与引用内容是否一致**。它只保证引用号合法，不保证 `[1]` 真的被用来支撑那句话。后者需要 entailment 模型，属于 U5.4 之外的重依赖。
5. **前端未改**。`generation` 字段已透出但页面没有渲染入口（离线/降级提示、fallback 标记都还看不见）。
6. **`RERANK` 与生成层无联动**。检索给 6 条，生成把它们全塞进 prompt，没有按分数截断 token。
