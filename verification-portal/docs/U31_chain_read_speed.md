# U31 — 兩件事：鏈讀取變快、QR 讓兩個偵測器都認

日期：2026-11-27（展示前一天）
動機：後台實跑一次四態演示，收據上的數字從「14 ms」變成「3.5 s / 11.1 s」，同時 preflight 的舞台 QR 一項亮紅。

## 1. 收據數字為什麼會走樣

`/showtime` 的每一步都會先寫一塊，再立刻驗一次。寫入會讓 `verify_chain()` 的
fingerprint 失效，於是「驗」的那一刀要**從 genesis 重掃全鏈**，每塊都重驗簽名。
掃描成本是每塊重新讀一次簽名方的 PEM 再解析一次公鑰，63 塊就把一次查驗拖到
3.6 秒——這一刻正好是觀眾盯著螢幕的那一秒。

改法（`app/crypto_util.py`）：`fetch_pubkey()` 以檔案的 `(mtime_ns, size)` 做記憶。
金鑰檔只有在登記或退役時才會被改寫，改寫即換 stamp，記憶自動失效，所以「不會
偷偷信任一把換過的公鑰」這條性質沒有被拿掉。

實測（同一條 63 塊的鏈，同一台機器，冷啟動各自獨立進程）：

| | 之前 | 之後 |
|---|---|---|
| 冷掃全鏈 `verify_chain()` | 3 652 ms | 849 ms |
| 舞台上「簽發」那一步 | 3.5 s | 123 ms |
| 舞台上「驗」那一步 | 11.1 s | 133 ms |
| 舞台上「註銷」那一步 | 1.5 s | 41 ms |

849 ms 是冷進程的數字；服務跑起來之後，同一輪演示裡看到的是 41–133 ms。
剩下的成本是 JCS 正規化 + 每塊一次 ML-DSA 驗簽，這部分**沒有**省，也不該省。

**仍開著**：海報上印的是 14 ms / 10 ms（安靜機器、27 塊時量的）。舞台上看到的
是幾十到幾百毫秒。同一個量級但不是同一個數，講的時候要主動說「這個數字會隨
機器負載浮動」，不要讓觀眾先發現。

## 2. QR：兩個偵測器都要認

換了隧道之後 host 變長，`/api/qr/{hash}` 回的東西 **OpenCV 的單碼偵測器讀得出、
多碼偵測器讀不出**。preflight 用多碼讀，於是紅燈；手機相機走的是多碼那一路，
所以這是真問題，不是測試太嚴。

改法（`app/main.py` 的 `qr()`）：挑 mask 時同時要求
`detectAndDecode` 與 `detectAndDecodeMulti` 都讀回同一個 URL；若沒有 mask 能同時
滿足，退回「至少一個讀得出」的那張，再不行才回落 mask 3。

驗證：同一張 PNG 單碼／多碼都解出 `…/verify?hash=…`；縮到 260 px + 高斯模糊 +
JPEG q70 的「拍照模擬」仍讀得出。preflight 回到 **11/11**。
