批次：U3.1（`admin` / `issuer` / `verifier` 三角色，批量签发通道按角色放行）

前置：U3.3 审计事件（已完成，双后端 12/12）

## 1. 边界：这一步只做"角色模型 + 一条通道"

U3.1 在计划里是"角色模型与端点授权"。若一次性把全部管理端点按角色重切，会同时改动**鉴权失败语义**和**审计写入路径**，出问题时无法区分是哪一类。因此本步只做两件事：

1. 建角色模型（`app/authz.py`），角色解析规则集中到一处；
2. 只把 **`POST /api/issue/batch`（批量签发）** 变成 `admin | issuer` 双角色通道，其余端点仍是 `admin` 独占。

**未做**：审计事件里的操作者身份（需要每个端点拿到并透传角色，牵动 6 处埋点签名，留到 U3.2 与 Key 字段一起动）。

### 2.1 角色表

| 角色 | 令牌来源 | 可做 |
|---|---|---|
| `admin` | `ADMIN_TOKEN` | 签发、撤销、签发方管理、API Key 管理、审计读取 |
| `issuer` | `ISSUER_TOKEN` | 仅批量签发 `POST /api/issue/batch` |
| `verifier` | 无令牌 | 验证、学生自查、公开日志、RAG（公开路由） |

`verifier` 在代码里只是**语义占位**：公开路由本来就不校验令牌，定义它是为了让角色表和审计将来能引用同一个词表，而不是再造一个隐式的"无角色"。

### 2.2 兼容规则（这条是本次的关键）

```
PUBLIC_MODE=1                     → 403，任何令牌都不放行（旧行为）
所请求角色中「没有任何令牌被配置」  → 放行（旧 _admin_required 的 demo 语义）
配置了令牌但令牌不匹配             → 401，文案逐字不变
```

也就是说：**不设 `ISSUER_TOKEN` 的部署，行为与 U3 之前完全一致**；`ISSUER_TOKEN` 是纯 opt-in。

## 3. 一个必须记下的实现缺陷（本轮真实踩到）

`_token_for()` 第一版写成：

```python
return str(cfg.ADMIN_TOKEN if role == ADMIN else cfg.ISSUER_TOKEN if role == ISSUER else "")
```

`ADMIN_TOKEN` 未配置时是 `None`，`str(None)` 得到字符串 **`"None"`**——真值。于是 `configured_roles()` 认为"有令牌已配置"，demo 场景下批量签发出 401 而不是 200。

这正是角色冒烟里 `open_default_batch: MISMATCH 401` 的根因。改为显式 `cfg.ADMIN_TOKEN or ""` 后 14 项全过。

**为什么值得记**：`str(None)` 是个不报错、不告警、只改行为的转换。如果只跑全量单测（默认无令牌、默认走 demo 路径），这条断言恰好也会通过——是本步专门写的角色冒烟把它抓出来的。

## 4. 单个端点改动

```python
@app.post("/api/issue/batch",
          dependencies=[Depends(authz.require_roles(authz.ADMIN, authz.ISSUER))])
```

`_admin_required` 保留原名与原签名（避免动 8 个端点的装饰器，也守住"公共 API 签名不变"红线），内部改为 `return authz.require_roles(authz.ADMIN)(x_admin_token)`。

**注意**：真实请求路径上 FastAPI 只走 `require_roles` 返回的 dependency，`_admin_required` 只在代码里被直接调用时生效。这是刻意保留的薄壳，不是死代码——删它就得改 8 个装饰器，风险大于收益。

## 6. 遗留

1. **审计不含操作者身份**：`require_roles` 已能返回角色名，但 6 处 `audit.record` 埋点没有接收它。补法有两种——给端点加 `role = Depends(...)` 参数（会改函数签名），或让 dependency 把角色写进 `request.state`（要给端点加 `Request` 参数）。两者都是小改动但需统一决策，留 U3.2。
2. **`ADMIN_TOKEN` 与 `ISSUER_TOKEN` 都是明文共享密钥**，无过期、无轮换、无失败计数锁定——正是 U3.2 的 Key 生命周期间题，只是这两条走环境变量而非 API Key 表。
3. **角色粒度仍粗**：`issuer` 只能批量签发，不能单条签发 `POST /api/issue`。若注册处需要单条补发，得再加一个白名单。
4. **API Key（employer 包）与角色体系尚未打通**：现在 API Key 走 `_api_key_required`，与 `authz` 平行存在两套凭证。合并会改变 employer 调用方的行为，需单独一步。
