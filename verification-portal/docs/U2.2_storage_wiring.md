## 2. 接线前识别的那颗雷，本步的处理

U2.1 报告里点出的陷阱是：`CHAIN_DIR` 可能被测试在导入后重新绑定，而模块若在导入期构造存储实例，路径就会早绑定，出现"测试全绿但换目录读旧文件"的隐性错误。

处理方式：**缓存键包含全部实时路径**。

```python
def _cache_key(backend):
    if backend == "sqlite":
        return ("sqlite", str(cfg.SQLITE_PATH))
    return ("json", str(cfg.BASE_DIR), str(cfg.CHAIN_DIR))
```

`store()` 每次调用按当前 `cfg.BASE_DIR` / `cfg.CHAIN_DIR` / `cfg.SQLITE_PATH` 算键；键变了就重建 bundle。因此：

- 默认（json）行为下，`BASE_DIR` 恒定、`CHAIN_DIR` 由测试在导入前注入 → 键稳定，bundle 只建一次，无重复 IO。
- 若运行期重绑 `CHAIN_DIR` → 键变化 → 自动换成新目录的 bundle，不会读到旧路径。
- 后端切换（json ↔ sqlite）→ 键不同 → 两个 bundle 并存，互不污染。

实测：`reset_store_cache()` 后重新读取，收据/Key/日志/通知全部仍在（见 §5 第 8 组），证明数据在库不在进程内存。

## 3. 逐字段保真：`total()` 的窗口语义

`public_log.verification_log.total()` 原来返回 `deque` 长度（上限 50）。若直接改成 `store.total()`，会变成**文件/表的全量计数**（可能是 2000），Log 页显示的数字会悄悄变大。

处理：`total()` 取 `min(store.total(), max_entries)`，`recent(limit)` 取 `store.recent(min(limit, max_entries))`。三种情形都还原了原语义：

| 场景 | 原实现 | 现实现 |
|---|---|---|
| 库里 3 条 | 3 | min(3, 50) = 3 |
| 库里 60 条 | 50（deque 满） | min(60, 50) = 50 |
| 库里 2000 条 | 50 | min(2000, 50) = 50 |

## 4. 其它保真点

1. **摘要盐不变**：`repository.key_digest()` 仍用 `gef26-apikey:` 前缀 + SHA-256，历史 Key 换后端后依然能校验通过。
2. **Key 对外视图不含敏感字段**：`list_keys()` 不返回 `hash` 与明文 key（校验见 §5）。
3. **`validate_key` 仍会写 `last_used_at`**，只是在 SQLite 后端变成一条 UPDATE。
4. **收据 ID 生成规则不变**：`RCP-{hex(时间)}-{4位大写 hex}`。
5. **通知的无 URL 情形**：只在有 URL 时才写 `url` 键，与旧记录形状一致（旧 jsonl 里既有行也不带该键）。

## 7. 本步未做（明确记录）

1. **`statuslist.py` 的撤销索引尚未接到 `RevocationIndexStore`**。原因：撤销索引是从链上 `revoked_records()` 派生的**缓存**，不是新事实源。接线要决定"何时写索引"（签发时、撤销时、还是启动重建），若在 `revoke()` 里顺手写，json 后端会多出一个此前不存在的 `data/revocation-index.json` 落盘文件——这会改变现有磁盘产物清单，属于需要单独确认的行为变化。留作 U2.3 处理。
2. **多 Worker 全量测试未跑**。SQLite 模式只做了单进程端到端冒烟；`scripts/run_all_tests.py` 的 12 个模块在 sqlite 后端下共享同一个 `SQLITE_PATH`（默认 `data/portal.sqlite3`），会跨模块累积数据、破坏各测试模块"从空库开始"的假设。要跑全量需按模块隔离 `SQLITE_PATH`，属测试基础设施改动，不在本步范围。
3. **连接池未做**。当前每操作一条短连接，演示规模可接受；真实并发量下再评估。
