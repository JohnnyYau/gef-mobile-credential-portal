## 1. 范围

计划里的 U3.2 是"Key 生命周期：过期、轮换、撤销原因、最近使用、失败计数锁定"。本步做前四项，**第五项（失败计数锁定）不做**，理由写在第 6 节——它不是"再补一个字段"的量级，需要独立的全局计数器，与 U2 遗留的 Redis 限流是同一个问题。

原则：**所有新增字段都是可选的，不设即不生效**。不带 `expires_in_days` 建出来的 Key 与 U3.1 之前完全等价（永不过期、无撤销原因），旧 JSON 记录与旧 SQLite 库都能直接继续用。

### 2.1 新增存储字段

| 列 / 键 | 类型 | 含义 |
|---|---|---|
| `expires_at` | float \| None | 绝对过期时刻；None = 永不过期 |
| `use_count` | int | 成功校验次数（默认 0） |
| `revoke_reason` | str \| None | 撤销原因（`staff left` / `rotated` / 自定义），截断 120 字符 |
| `replaced_by` | str \| None | 轮换后指向新 Key id |

老记录缺这些字段时按 `None` / `0` 读，不报错——JSON 侧用 `rec.get()`，SQLite 侧靠默认值。

### 2.2 老库补列（这条是本次最容易出事的点）

`_SCHEMA` 里的 `CREATE TABLE IF NOT EXISTS` 对**已存在的库**不会加列。因此 `SqliteBackend.ensure_schema()` 在建表后调用 `_ensure_api_key_columns()`：读 `PRAGMA table_info(api_keys)`，缺哪列就 `ALTER TABLE ... ADD COLUMN`。

- 纯 additive，不改不删任何旧列；
- 幂等（列已存在则跳过），每次启动都跑，代价是一条 PRAGMA；
- 不依赖 `MIGRATION_VERSION`——那个版本号是 json→sqlite 一次性迁移的守卫，混用会让老库被误判为"已迁移"。

冒烟里专门造了一个**旧 schema 的 sqlite 库**（只有六列），boot 后确认四列全部补上、且能正常插入带 TTL 的新 Key。

### 2.3 端点

| 端点 | 变化 |
|---|---|
| `POST /api/admin/apikeys` | body 可带 `expires_in_days`（正整数；0/缺省/非法 → 永不过期）；返回体新增 `expires_at` |
| `GET /api/admin/apikeys` | 每个 Key 多返回 `expires_at / use_count / revoke_reason / replaced_by`（additive） |
| `DELETE /api/admin/apikeys/{kid}` | 新增可选查询参数 `reason` |
| `POST /api/admin/apikeys/{kid}/rotate` | **新增**。撤销旧 Key（`revoke_reason="rotated"`、`replaced_by=<新 id>`）并返回新密钥，明文只出现一次 |

轮换对**已过期但未撤销**的 Key 也生效——过期是"不能用"，撤销是"作废"，两者语义不同，轮换按状态判断（`revoked` 才算不能转）。

## 3. 行为变化（哪一处真的变了）

只有一处**主动行为改变**：设置了 `expires_in_days` 的 Key，过期后 `validate_key()` 返回 `None`，即 API 请求得 401。

其余全部是 additive：不设 TTL 的 Key 生命周期与之前逐字一致；`list_keys()` 多几个字段；`DELETE` 多了可选参数。这是刻意的——现有 108 条测试全部按旧契约写，若默认行为变动，一次回归就会看到一堆红。

## 5. 一个安全性上的取舍

`use_count` 与 `last_used_at` 是**每次校验都写盘**的（JSON 侧重写整个文件，SQLite 侧一条 UPDATE）。这带来两个后果：

1. JSON 后端下高频校验会放大 IO——原本只更新 `last_used_at` 就已经写盘，本步只是多改了一个整数，量级没变；
2. 计数是**旁路观测**，不是配额判定。它不阻止任何请求，不参与限流。

若将来要把 `use_count` 变成配额（"这张 Key 每月最多查 1000 次"），写入就会进入拒绝路径，需要先解决并发下"读-改-写"的竞态（JSON 侧靠模块锁、SQLite 侧靠单连接 UPDATE，目前都在锁内，勉强够用但不可跨进程）。这条写在这里，避免以后误以为已有配额能力。

## 6. 为什么不做"失败计数锁定"

需求里的"失败计数锁定"指：某把 Key 连续认证失败 N 次后锁定一段时间。当前实现做不了，原因是**令牌错误时根本不知道是哪把 Key**——输入的字符串算不出对应记录（只存了加盐摘要，这是设计上的正确选择）。

可行的做法只有两种：

- 按 **来源 IP** 计数（与现有 `SlidingWindowLimiter` 天然契合，但 IP 在代理后不可信）；
- 全局失败计数（任何 401 都累加），误伤面太大。

两种都需要一个**跨进程共享的计数器**——正是 U2 遗留的 `TODO[external-redis]`（当前 `SlidingWindowLimiter` 是进程内内存）。所以在 U2 的 Redis 适配落地之前，加"失败锁定"只会得到一个单进程有效、重启即失忆、多 Worker 各算各的假防护。**留到 Redis 那一步一起做，比现在做一个看起来有、实际没有的锁定更诚实。**

## 7. 遗留

1. **失败计数锁定未实现**（理由见第 6 节，依赖 U2 的 Redis 项）。
2. **审计未记录角色与 Key 名称细节**：`apikey.rotate` 记了 `old -> new`，但没记操作者角色（U3.1 遗留项，需统一决策怎么把角色透传进 6 处埋点）。
3. **Key 与角色体系仍是两套凭证**：API Key 走 `_api_key_required`，角色令牌走 `authz`，互不识别。
4. **无配额**：`use_count` 只是观测值（见第 5 节）。
5. **UI 未跟**：`static/index.html` 的 API Key 面板没有 TTL 输入框、没有轮换按钮、不显示 `use_count`。本步只动后端，前端留到需要演示时再做。
