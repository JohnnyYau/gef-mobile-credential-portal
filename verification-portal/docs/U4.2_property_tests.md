## 3. 四组属性与实测结果

### 3.1 规范化确定性（3 条）

| 测试 | 断言 |
|---|---|
| `test_key_order_does_not_change_the_hash` | 任意 JSON（随机嵌套、随机标量）→ 随机打乱所有字典键序 → 哈希不变 |
| `test_hash_is_stable_across_repeat_calls` | 经 `json.dumps/loads` 往返后哈希不变 |
| `test_digest_is_base64url_without_padding` | 摘要不含 `=`、`+`、`/` |

用 `st.recursive` 生成嵌套结构，`max_examples=60`、`max_leaves=8`。另有一条负向：不支持的算法名必须抛 `ValueError`。

### 3.2 Merkle 根一致性（4 条）

- 单叶：根 == 该叶（`merkle_root([h]) == h`）；
- **奇数层复制最后一叶**：属性测试按同样规则独立重算一遍再比对（不是复用被测函数算"期望值"——那样同错同过）；
- **顺序敏感**：两片不同叶子交换 → 根不同；
- 空叶列表抛 `ValueError`。

第二条是关键：如果直接调 `merkle_root` 算期望值，测试等于自证。这里在测试里**手写一遍归并逻辑**，两边独立才叫验证。

### 3.3 篡改必失败（4 条）

| 测试 | 断言 |
|---|---|
| `test_any_single_field_change_changes_the_hash` | 随机挑一个标量字段换成同类型不同值 → 哈希必变 |
| `test_extra_key_changes_the_hash` | 多一个键 → 哈希变 |
| `test_dropping_a_key_changes_the_hash` | 少一个键 → 哈希变 |
| `test_type_swap_changes_the_hash` | `1` vs `"1"` → 哈希变 |

最后一条针对的是**宽松序列化**：若实现把数字和字符串都按文本拼接，`1` 与 `"1"` 会撞哈希，篡改就能静默通过。JCS 不这么做，这条把该性质钉住。

### 3.4 验签异常路径（8 条）

全部断言**返回 False 而不是抛异常**：

| 输入 | 结果 |
|---|---|
| 随机乱码签名 + 随机 nonce + 随机 payload（属性化） | False |
| 空签名 | False |
| 错 nonce | False |
| 非 base64 签名（`!!!not base64!!!`） | False |
| `object()` 冒充公钥 | False |
| 不存在的哈希算法名 | False |
| 截半的签名 | False |

外加一条正向对照：同一签名对**原 payload** 为 True、对改过字段的 payload 为 False——证明上面的 False 不是因为验签恒假。

### 3.5 算法分派矩阵（3 条）

ML-DSA_65 / RSA-2048 / ec.SECP256R1 各跑同一套：

- 正签正验 → True；
- 同签名换消息 → False；
- 同消息换 nonce → False；
- 同消息换公钥 → False。

每个子测试都 `subTest(algo=...)`，一种算法坏了不会掩盖另两种。密钥在 `setUpClass` 里生成一次（ML-DSA 生成比哈希慢几个数量级，不能每条测试都生成）。

## 4. 一个被测试纠正的错误认知（必须记）

我最初写了这条断言：**固定 nonce 时应得到字节相同的签名**，理由写的是"ML-DSA 和 RSA-PSS 都从同一 nonce+摘要重新导出"。

实跑直接失败：

```
AssertionError: '1T1LbQH-...' != 'dUfYHKJN-...'   (ML_DSA_65)
AssertionError: 'Y1iV53jR-...' != 'CbW48fBr-...'   (RSA-2048)
```

真相：**RSA-PSS 每次随机取盐，ECDSA 每次随机取 k**，固定 nonce 只固定了"被签名的消息"，固定不了签名值。（ML-DSA 在这个实现里也不是字节复现的。）

于是把测试改写为两条更准确的性质：

1. 固定 nonce ⇒ 两次签名**都可验**（消息确实一致）；
2. RSA-PSS 与 ECDSA ⇒ 两次签名值**不同**。

第二条不是"测试将就实现"，它是个有实意的结论：**任何按签名值去重发放凭证的设计都是错的**，必须按 payload 哈希去重。这条现在写进了测试注释，以后谁想加"签名去重"会先撞到它。

## 5. 顺带修正一处陈旧注记

`requirements-dev.txt` 里写着 `# Test runner + static analysis (all MIT/BSD licensed)`，但 `hypothesis` 是 **MPL-2.0**（弱 copyleft，按文件生效，非 GPL）。

`hypothesis>=6.112` 本来就在依赖里（U0 就写了），说明这条注记在 U0 时就是错的，只是没人核对。本步既然要引用它，就把注记改成实际情况：

```
# pytest MIT, ruff MIT, mypy MIT, hypothesis MPL-2.0 (permissive /
# file-level copyleft — not GPL, acceptable here)
```

按项目红线（拒绝 GPL-3.0、付费、闭源、强传染），MPL-2.0 属于可接受范围，但**必须写明**，不能让"all MIT/BSD"这句错话继续躺着。

## 7. 属性测试没覆盖的地方（如实列出）

1. **链上真实块**：本步只测 `crypto_util` 层（哈希、Merkle、签名）。`verify_block` / `verify_chain` 需要真实链目录，属 U4.3 的"损坏注入用例"。
2. **并发**：没测多线程同时 `append_block` 的行为（`chain_core._lock` 只在进程内）。
3. **大 payload**：`max_leaves=8`、字段长度上限 12，没有针对 MB 级 payload 的耗时/内存性质。
4. **浮点边界**：策略排除了 NaN/Infinity（JCS 本身不支持），所以"非法浮点应抛错"这条没测——如果以后要保证，得单独加一条负向用例。
