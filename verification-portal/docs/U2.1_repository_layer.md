## 1. 本步做了什么 / 没做什么

**做了**：五个存储的读写接口（Protocol）、与现有文件格式逐字段对齐的 `Json*` 实现、共用一套 schema 的 `Sqlite*` 实现、一次性迁移 + 迁移版本号守卫、后端选择配置。

**没做（U2.2 范围）**：**尚未把端点模块切到仓储层**。这是计划里风险条款要求的次序——"先只读切库、再切写"。当前 `apikeys.py` / `receipt_registry.py` / `public_log.py` / `notifier.py` 仍走原有代码路径，`STORAGE_BACKEND` 默认 `json`，因此**线上行为与 U1 完全一致**（108 用例逐条证明）。

这样切分的理由：一次性把四个模块换掉会在同一步里同时引入"接口适配"和"写入路径变更"两类风险，回归失败时无法区分是哪一类。本步先把两套实现跑通并证明等价，U2.2 只做接线。

## 3. 存储契约（两套实现必须逐字段一致）

| 存储 | 关键方法 | 字段形状 |
|---|---|---|
| `ApiKeyStore` | `create_key` / `list_keys` / `revoke_key` / `validate_key` | key 记录 `{id,name,created_at,last_used_at,revoked,hash}`；对外视图**不含** `hash` 与明文 key |
| `ReceiptStore` | `register` / `get` | `{receipt_id,hashed_document,verdict,verified_at,endpoint}`；ID 格式 `RCP-{hex(时间)}-{4位大写hex}`；`RECEIPT_REGISTRY_CAP` 环形裁剪 |
| `LogStore` | `record` / `recent` / `total` | `{time(整数秒),hash_prefix(前12字符),verdict}`；空 verdict 记 `UNKNOWN` |
| `NotificationStore` | `record` / `recent` | `{time,to,subject,status,detail}`，有 URL 时才带 `url` |
| `RevocationIndexStore` | `upsert` / `get` / `all` | `{hashed_document,issued_height,revoked,reason,effective_at,updated_at}`，以哈希为主键 |

几处容易走样的细节，已刻意对齐：

1. **`hash_prefix` 是前 12 个字符**（原 `public_log` 的 `[:12]`），不是 8 也不是 16。
2. **时间取整**：日志与通知落库用 `int(time.time())`，Key 与收据保留浮点。
3. **`revoked` 对外是布尔**：SQLite 存 0/1，读出时转 `bool`，否则调用方 `if rec["revoked"]` 在 SQLite 后端拿到 0 会静默放行已撤销 Key。
4. **收据裁剪按插入序**：SQLite 用自增 `seq` 而不是 `verified_at`，因为补录旧时间戳不应把新记录挤掉。
5. **日志 `recent()` 返回升序**：SQL 先 `ORDER BY seq DESC LIMIT n` 再反转，避免调用方拿到倒序列表。

## 4. 并发与连接管理（U2.3 的前置部分）

- 写操作串行化：每个存储持有一把 `threading.Lock`，覆盖"读—改—写"整个区间（JSON 实现沿用原模块的锁粒度）。
- 连接生命周期：`SqliteBackend` 每操作开一条短连接、`finally` 关闭，用完即还；不开全局长连接，因此**没有跨线程共享 connection** 的问题，崩溃后也不会有悬挂事务。
- 崩溃恢复：`journal_mode=WAL` + `synchronous=NORMAL`；schema 用 `CREATE TABLE IF NOT EXISTS` 幂等创建，`ensure_schema()` 由 `_init_lock` 双检，重复调用无副作用。
- **已知限制**：短连接模式在每请求多次读写时会有连接开销。演示规模（单机、单进程）可接受；连接池留到接入真实并发量时再评估，不在本批次扩范围。

## 5. 迁移

`migrate_json_to_sqlite()` 读 4 个旧数据源：`data/apikeys.json`、`data/receipts.json`、`<chain-dir>/../public-log.jsonl`、`<chain-dir>/../notifications.jsonl`。

- **幂等**：成功后写 `meta` 表 `migration_version='1'`；再调用直接返回 `{"already_migrated": true, ...}`，不重复导入。
- **插入策略**：Key 与收据用 `INSERT OR IGNORE`（按主键去重），日志与通知是追加型、无自然主键，用普通 `INSERT`（迁移只跑一次，不会重复）。
- **不迁移的**：链区块（仍为 append-only JSON，作为审计导出物）、`rawjsondocs` 明文索引（按计划后续再评估）。

### 接线前必须解决的一个陷阱（已识别，未处理）

四个模块的路径依赖现状**不是**统一的：

- `public_log.verification_log = PublicLog()` 在**模块导入时**实例化，`_log_path()` 当时已把 `CHAIN_DIR.parent` 算进 `self._path`。测试通过 `CHAIN_DIR` 环境变量在**导入前**注入来隔离（`tests/_bootstrap.py` 的做法）。若把仓储实例也在模块导入时构造，就会把这个早绑定固化，**任何运行期改 `CHAIN_DIR` 的测试都会读到错误目录**。
- 因此接线必须**惰性构造**（按需 `_store()`），且 `LogStore` 需要保住在内存中的尾部（当前 `PublicLog` 的 `deque`）——每次调用都新建 `JsonLogStore` 会丢掉未落盘前的最近记录语义。

这条约束不解决就直接换实现，会出现"测试全绿但换目录后读旧日志"的隐性错误，属最危险的一类回归。U2.2 需按此逐模块处理，而不是批量替换。
