## 1. 计划原文与我最终实现的东西

计划原文：

> 字段级哈希与披露视图：持证人可选择隐藏 DOB/学号，验证方只看到承诺与披露字段；不承诺 zk 证明强度。

我第一版按字面做了「盐值 + 逐字段承诺」，写完测试就发现它有个致命弱点：**承诺无法与链上内容建立任何关系**。验证方拿到 `commitment = hash(salt||value)`，既打不开（没有 value），也没法核对它是否真的是链上那份凭证里的 DOB——因为该字段已被隐藏，链上只有整份文档的哈希。

也就是说，那种视图只能证明「这份视图自称来自某个凭证」，**证明不了任何披露内容**。看起来更保护隐私，实际上什么都没证明。

随后我读了 `issue_payload` 才意识到链的结构早就支持更强的做法：

```python
h_pp = hash(PersonalParticulars)
h_ai = hash(AcademicInfo)
h_di = hash(DocumentInfo)
HashedDocument = merkle_root([h_pp, h_ai, h_di])
```

**链上本来存的就是章节级哈希**。于是改成章节级披露：

- 隐藏 `PersonalParticulars`（DOB、学号都在这里）；
- 展示 `AcademicInfo`、`DocumentInfo`；
- 验证方重算展示章节的哈希，与链上 `HashedAcademicInfo` / `HashedDocumentInfo` 逐一比对；
- 再用链上未展示章节的哈希做 Merkle 根，与 `HashedDocument` 比对。

这样披露的内容是**密码学绑定到链上的**：改一个字就必然失败。隐藏章节的承诺就是它自己的链上哈希——不需要盐，也无法伪造。

这比盐值方案强一个量级，而且**没有给链加任何字段**，旧链与新链都不用动。

## 3. 视图长什么样

```json
{
  "credential_hash": "<HashedDocument>",
  "content_hash_algo": "sha3_512",
  "disclosed_sections": {"AcademicInfo": {...}, "DocumentInfo": {...}},
  "hidden_sections": ["PersonalParticulars"],
  "section_hashes": {"AcademicInfo": "<h_ai>", "DocumentInfo": "<h_di>"},
  "hidden_section_hashes": {"PersonalParticulars": "<h_pp>"},
  "commitments": {},
  "unbound_sections": [],
  "assurance": "disclosed sections are cryptographically bound ... not a zero-knowledge proof."
}
```

`assurance` 是**每个视图都带的免责声明**，写清「隐藏章节只承诺哈希、字段承诺只能由持有人事后打开、这不是 zk 证明」。任何调用方都能读到这句话，不能误认为它是证明系统。

## 4. 四类必须失败的情况

| 情况 | 机制 |
|---|---|
| 改披露章节里任何一个字段 | 该项哈希对不上链上 `Hashed{Section}` |
| 换一个 `credential_hash` | 与链上记录不一致 |
| 同一章节既披露又隐藏 | 显式报 `sections both disclosed and hidden` |
| 链上记录自身不自洽 | Merkle 根重算与 `HashedDocument` 不符 |

另外：**隐藏全部章节被拒绝**（`Cannot hide every section — the view would prove nothing`）。一个什么都不展示的视图没有意义，允许它只会给人「隐私很强」的错觉。

**字段级隐藏**保留了，但它会破坏所属章节的哈希，视图会在 `unbound_sections` 里明写「该章节不再可验证」，验证时该项必然失败。这是刻意的：宁可报「不可绑定」，也不假装它还成立。

## 5. 过程中修掉的两个真缺陷

### 5.1 视图别名污染原文档（最危险的一个）

`make_disclosure` 第一版直接 `disclosed[section] = body`——把调用方的 dict **引用**放进视图。后果：调用方（或验证方）改一下视图里的 `DegreeName`，**原始凭证 JSON 也跟着变**。测试里正是先跑「篡改视图」再跑「绑定校验」，于是后面的用例读到被污染的文档而失败，这才把问题暴露出来。

已改为 `copy.deepcopy`，并写了注释说明原因。

**这条如果漏了，等于门户有个「改视图 = 改凭证」的后门。**

### 5.2 `hide_fields` 路径约定不一致

`_leaves` 返回的是章节内相对路径（`Honour`），而 `hide_fields` 传的是全路径（`AcademicInfo.Honour`），首版直接 `p in leaves` 判断，导致永远「未知字段」。改为按首个点号拆分后比对。

## 7. 明确没做到的部分

1. **真 zk 完全没做**。不能证明「DOB 在某区间」「学号以某前缀开头」「成绩在前 10%」这类谓词。计划原文就说不承诺 zk，这里再确认一次。
2. **隐藏章节的内容没有可验证性**，只有哈希。验证方无法知道里面是 DOB 还是别的什么，也不知道字段个数。
3. **没有「最小披露」策略**。默认隐藏 `PersonalParticulars`，但调用方可以自行传任意章节组合；谁都不限制「你到底该披露多少」。要做得体面需要策略对象（与 U5.3 的脱敏策略同源），现在没做。
4. **`/api/disclose` 无鉴权、无审计**。它读 `rawjsondocs/` 并返回凭证部分内容，本质上是一个「按哈希取明文」的接口。当前门户是演示性质，`/api/student/{sid}` 那条也走 DOB 门槛；这个新接口目前没有任何门槛。**这是一个明确的安全遗留**，要么加 admin/issuer 角色，要么加持有人签名令牌——需要与 U3 的角色体系一起决定，不在本步擅自加。
5. **未在前端暴露**。没有 UI 入口，纯粹是 API 能力。
