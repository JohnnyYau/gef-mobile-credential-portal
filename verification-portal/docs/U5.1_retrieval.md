## 2. 版本戳：为什么必须从 mtime 换成摘要

旧实现：

```python
stamp = (last_height, max(mtimes))
```

`max()` 有一个真实的失效场景：**同一时间粒度内的两次写入看不出变化**。NTFS 的 `st_mtime` 与 FAT 的 2 秒粒度都可能把「追加了一个块」压进同一个时间戳，索引就会继续服务旧语料——而这种错误不会报错，只会让检索结果悄悄变旧。

新实现按 **(name, mtime_ns, size) 排序后做 sha256**，得到 `(height, digest[:32])`。`mtime_ns` 纳秒级，加 `size` 做双保险。

## 3. 向量缓存

### 3.1 位置刻意放在链目录之外

```
data/demo-chain/            ← 链
data/rag-cache/demo-chain-hash-ngrams-v1-1024.npz   ← 缓存
```

不放进链目录的理由很具体：`build_corpus` 会枚举 `blocks/` 与 `rawjsondocs/`，任何被放进这两个目录的文件都会**改变语料本身**并触发版本戳变化，形成「缓存导致重建」的自激。

### 3.2 命中条件

```python
meta = {"stamp": [...], "entry_ids": [...], "backend": ..., "dim": ...}
```

四者全部一致才复用；任一项不同就重编码。`load_cached_vectors` 任何异常都返回 `None`（损坏的缓存只该换来一次重建，不该让检索挂掉）。

### 3.3 我在这里踩到的坑：缓存从来没写成功

`np.savez` 在路径不以 `.npz` 结尾时会**自己再加一个 `.npz`**。我第一版写成：

```python
tmp = path + ".tmp"
np.savez(tmp, ...)      # 实际写出 x.npz.tmp.npz
os.replace(tmp, path)   # 找不到 x.npz.tmp → OSError → 返回 False
```

`save_vectors` 用 `except OSError: return False` 吞掉了它，于是**每次运行都显示 `cache=built`**，看起来「缓存生效了但没命中」——实际从未写过盘。

这是「静默失败」的典型：功能表面正常（重建照样能用），只有盯着 `stats()['cache']` 反复显示 `built` 才可疑。我已改成 `path[:-4] + ".tmp.npz"` 并在注释里写明原因。

### 3.4 实测

| 场景 | `stats()['cache']` |
|---|---|
| 首次构建 | `built+saved` |
| 同进程再建一个索引 | `hit` |
| 链增长后 | 戳变化 → 重建并写入新缓存 |
| 缓存文件损坏 | 视作 miss → 重建（不抛异常） |

## 4. 重排：先排除混淆变量，再决定默认值

第一版评测给出 `recall@6` 从 0.8 → 1.0，看起来重排很灵。但我打开重排时**同时把候选窗口从 k 扩到 2k**——召回的提升可能全部来自窗口，跟词法加分无关。

于是把两者拆开测：

| 配置 | recall@6 | hit@1 | MRR |
|---|---|---|---|
| 重排关，窗口 6 | 0.800 | 0.400 | 0.567 |
| 重排关，窗口 12 截断到 6 | 0.800 | 0.400 | 0.567 |
| **重排开，窗口 12 截断到 6** | **1.000** | **0.500** | **0.653** |

第二行与第一行完全相同，说明**扩窗本身毫无收益**；第三行的提升全部来自词法重排。据此把 `RERANK_ENABLED` 默认改为 `True`（`RAG_RERANK=0` 可关，回退到旧行为）。

重排的契约写死在代码里：**只重排，不增不减**。`rerank()` 的输入输出 id 集合必须一致（有测试断言），这样即使加权重调坏了，召回上限也不会掉。

## 5. 融合函数

```python
fuse_exact_and_vector(exact, vector_views, k)
```

规则：精确哈希命中永远排第一（查询里字面出现 40+ 字符的哈希，是比任何相似度都强的信号）；按 id 去重，避免同一凭证占两个槽位；最后截断到 k。

抽成纯函数后，调参不再需要改 `search()` 的控制流。

## 7. 基线数字与它的适用范围（重要）

`scripts/rag_eval.py` 的基线是在**当前环境**跑出来的：

```
chain=...\data\demo-chain height=11 queries=10
rerank-off: recall@6=0.800 hit@1=0.400 mrr=0.567
rerank-on : recall@6=1.000 hit@1=0.500 mrr=0.653
```

必须说明三点：

1. **本环境没有 `sentence-transformers`**（`No module named`），实测用的是 `hash-ngrams-v1` 兜底嵌入。装上游模型后数字会变，**这组基线只对兜底嵌入成立**。
2. **golden set 只有 10 条**。10 条上的 recall 差 0.2 就是两条 query，统计意义很弱，存在过拟合风险——`RERANK_WEIGHT=0.25` 也是在这个小集上定的，没有做留出验证。
3. 评测脚本在预期 id 连 `k=50` 都取不到时会以非零退出码报「GOLDEN SET BROKEN」，防止语料变化后基线悄悄失效。

## 8. 明确没做到的部分

1. **没有真正的语义重排**。词法重叠只能对齐字面 token，同义改写（"diploma" vs "certificate"）拿不到加分。真正的 cross-encoder 重排是重依赖，本批不引入。
2. **缓存没有淘汰与上限**。链一旦变化就写一个新文件，旧文件留在 `rag-cache/` 里不管。多次演示/测试会积累垃圾。`rag-cache` 目前不在 `.gitignore` 的忽略清单里，需要补。
3. **多进程同时重建没有加锁**。两个 worker 同时 `save_vectors` 会互相覆盖（`os.replace` 原子，所以不会读到半个文件，但会重复劳动）。单进程 uvicorn 下无影响。
4. **评测集不是回归测试**。`rag_eval.py` 是手动脚本，没进 `run_all_tests.py`：因为嵌入后端随环境变化，把它当断言会让 CI 变成随环境飘的红绿灯。它只产出数字供人对比。
5. **检索层的 `stats()` 新增了 `cache`/`rerank`/`stamp` 三个键**，`/api/rag/status` 直接透传，响应体会多字段——属于新增，不改变既有字段。
