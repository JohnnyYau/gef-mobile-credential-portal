## 2. 评测集本身

`scripts/qa_eval.py` 与 U5.1 的 `scripts/rag_eval.py` 是**两条不同的线**，不要混：

| | `rag_eval.py`（U5.1） | `qa_eval.py`（U5.4） |
|---|---|---|
| 测什么 | 检索层：候选里有没有正确答案 | 生成层：答案对不对、引用指得对不对 |
| 指标 | recall@6 / hit@1 / MRR | hit_rate / citation_accuracy / fallback_contract |
| 输入 | 10 条检索 query + 期望条目 id | 10 条自然语言问句 + 期望事实 + 期望引用目标 |
| 数据 | `data/demo-chain`（存量链） | 临时链，脚本内自发签发，可复现 |

评测链**每次现建**：`ensure_chain()` 播种，然后签三份凭证——一份保持 VALID（LAM SIU MING / 55554444）、一份立刻撤销（CHAN TAI MAN 样张）、一份第二个学生（NG KA LOK / 88990011）用来做引用精度对照。链条目、块高、哈希每次不同，但**问句与期望是按事实写的**，所以指标可复现。

覆盖的八类（计划要求全覆盖）：

| 类别 | 用例 | 期望 |
|---|---|---|
| 哈希 | `hash-status` / `hash-revoked` | VALID / REVOKED，引用对应哈希前缀 |
| 姓名 / 学号 | `name-status` / `student-id` | REVOKED / VALID，引用对应凭证 |
| 课程 | `courses` | 转录含 `lists:`，引用任一凭证 |
| 计数 | `count` | `blocks in total` + `ISSUE`，引用 `chain:` |
| 签发方 | `signer` | `UNIVERSITY OF UTOPIA`，引用 `chain:` |
| 完整性 | `integrity` | `integrity is OK`，引用 `chain:` |
| 最新块 | `latest-block` | `latest block is height`，引用 `block-` |
| 无记录兜底 | `no-record` | `No credential is recorded`，**要求 fallback 标记为 true** |

`no-record` 那条是刻意设计的：它的正确答案**没有可引用的记录**，所以契约不是"引用为空"，而是"系统告诉调用方这批来源是兜底上下文"。这条用例在第一版里是白过的（`expect_source: []` 恒真），加上 `fallback_contract` 之后才有意义。

## 3. 跑出来的两个真缺陷

这就是评测集存在的理由——写报告时才发现的两个问题，都不是读代码能看出来的。

### 3.1 链级规则硬编码 `[1]`，实际引用了一条无关凭证

第一轮结果：

```
FAIL signer  answered=True  cited=False
sources=['credential:mKqXBPRo...']       ← 一条 NG KA LOK 的凭证
```

`_r_signer` 返回 `("Trusted data signer(s): …", [1])`。`[1]` 的意思是"第 1 条检索记录"，而它**只有在第 1 条恰好是 `chain:info` 时才成立**。这次检索把一张凭证排到了第 1，于是「谁是这个链的签发方」这条答案下面挂着一张学生文凭——答案对、来源完全错。这类错误人工点几下很可能点不出来，因为答案文本是漂亮的。

受影响的规则共五条：`revocations` / `counting` / `signer` / `algorithm` / `integrity`（都不读 `records`，只是惯例性地写 `[1]`）。`latest-block` 没事，它本来就按 height 精确匹配记录。

修法：

```python
def _chain_cite(records):
    for i, r in enumerate(records, 1):
        if r.get("kind") == "chain" or str(r.get("id", "")).startswith("chain:"):
            return [i]
    return []
```

拿不到链级记录就**返回空**——在 U5.2 之后，空引用是合法状态（`zero_citations` 标注 + 前端 fallback 标记），比"随便指一条"诚实得多。

### 3.2 评测集自己写错了：同一份凭证既当有效又当撤销

第一轮 `hash-status` 失败：

```
FAIL hash-status answered=False cited=True
```

因为我先 `issue(SAMPLE_DIPLOMA)` 得到 `_diploma`，再把**同一份**的哈希拿去做撤销，然后用它的哈希问「状态」。内容相同 → 哈希相同 → 那个文档确实已经撤销，答案返回 `REVOKED` 是对的，是**期望写错了**。

改成三份独立凭证（有效 / 已撤销 / 第二学生）后通过。这条错误说明：**评测集的 fixture 也要被评测**——如果 fixture 错了，它会把正确实现判成失败，然后你去"修"一个没坏的东西。

## 6. 明确没做到的部分

1. **`qa_eval.py` 不在 `run_all_tests.py` 里**，不是回归门禁。原因与 `rag_eval.py` 相同：它依赖嵌入后端，本环境是 `hash-ngrams-v1` 兜底，装了 `sentence-transformers` 后检索排序会变，指标可能从 1.0 掉下来——那是**环境差异**而不是回归。把它当红线会让测试随机器变红。它只产出可对比的数字。
2. **10 条用例太少**。`joint` 从 1.0 掉到 0.9 只是错了一条。而且 10 条里 7 条都是"读一个字段"型问题，对**同义改写、多跳问题、否定问题**（"除 CHAN TAI MAN 之外还有谁被撤销？"）完全没有覆盖。
3. **命中判定是子串匹配**。答案说「VALID on the chain — issued at height 3」与期望 `VALID` 匹配；但如果答案错写成「NOT VALID」也照样包含 `VALID` 子串，会被判过。真正的判定需要结构化答案，本项目没有。
4. **只测离线引擎**。脚本强制 `DEEPSEEK_API_KEY=None` / `OLLAMA_BASE_URL=None`，LLM 路径的答案质量与引用正确率**完全没有基线**。LLM 引用是从答案文本里解析的（U5.2），那套逻辑的准确率没有任何评测支撑。
5. **引用正确率只检查"期望目标在不在 sources 里"**，不检查"多余来源是否相关"。`name-status` 会同时引用 person 记录和凭证记录，两者都合理；但如果它多挂一条别人的凭证，当前指标看不出来。更严的做法是对每条 source 判定是否被答案使用——需要答案与来源的对齐，本批没有。
6. **`no-record` 的兜底来源仍然难看**：5 条上下文（3 张别人的凭证 + `chain:info` + 一个块）挂在一个「查无此人」的答案下面。这是 U5.2 保留的既有兜底行为（有 `sources_are_fallback` 标记，但 UI 没渲染）。语义上没错——它们是检索上下文——但作为"来源"展示会误导。**未修**，因为改它会动 `/api/chat` 的 `sources` 语义，属产品决策。
7. **没有分类型统计**。八类各 1–2 条，没法说"哪类最弱"。
